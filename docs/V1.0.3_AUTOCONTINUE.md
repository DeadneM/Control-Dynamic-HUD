## Evidence and implementation

Read-only inspection of the installed game assets (menu.ui and persistent.ui):

- ShowMenu payload uses m_bIsPauseMenu and m_bSaveAvailable. MainMenuRoot renders
  the Continue EventButton only when the latter is true.
- That button uses the exact event OnContinueGameClicked. EventTriggerBehaviour
  sends it through engine.trigger(event, ...eventArgs), without confirmation.
- The menu uses .main-menu-root / .main-menu-root--hidden, .app--pause-menu and
  confirm-box--active. Startup EULA/privacy/DLC flags are explicit in ShowMenu.
- Actual input names (OnNavigateUp/Down/Left/Right, OnSelect, OnCancel, OnStart,
  OnOptions, OnPrev/Next, OnX/Y) come from the shared InputEvent constants.

New settings: [Startup] AutoContinue=0 and AutoContinueDelayMs=2000 (0-10000ms).
Existing INIs missing these keys keep the option off. Public menu protections
and diagnostics stay 0; all other settings and accepted behavior are retained.

Only when enabled, use the existing main-menu factory/ready/Page::bind hook path.
Queue a separate auto-continue listener in the first validated Page::bind window
after native visual/base setup, before the menu event dispatch. A native process
latch offers it only on the first menu-ready call. The existing navigation
wrapper behavior, cleanup and save-protection guards are preserved. The wrapper
exposes its original subscription function so auto-cancellation callbacks can
subscribe without being navigation-wrapped; engine.off then removes the exact
registered functions. Combined-wrapper cleanup is covered by a regression test.

The JS listener waits for the actual ShowMenu payload, requires a non-pause
non-demo menu with a save, rejects startup dialogs, waits for a connected,
visible main-menu root, then uses the configured delay before requesting the
exact normal Continue event. It never sends generic Select, New Game or Mission
Select. It does not read, delete, choose or write save files.

Keyboard/mouse/wheel/touch or known controller menu events cancel the request
without consuming the player's input. Manual Continue, a second ShowMenu,
context/engine change, confirmation UI, or hiding a previously visible menu
also cancels it. After 30 seconds without readiness, stop. Mark done and remove
listeners/timers BEFORE native dispatch; failures do not retry an uncertain load.
No early pre-ready fallback: if the verified bind window is unavailable, skip
automatic Continue and preserve normal menu behavior/background.

Native logs record configuration and listener injection only; neither is proof
of loading. No new native detour or game memory patch is introduced beyond
using the established optional menu hook path. No full-DOM observer or per-frame
script injection. At AutoContinue=0, no auto script, listeners or timers run.

## Manual beta test and rollback

Back up the installed DLL and keep the personal INI. Do not enable other
experiments for this test. Start with AutoContinue=0 and verify ordinary startup,
menu navigation/background, guards, HUD/F1, Mission Log and Launch/fade behavior.
Then test AutoContinue=1 with AutoContinueDelayMs=2000 and an existing save: the
game should load the same save as a manual Continue. Return to the main menu:
it must stay there. In a fresh launch, navigate or press Escape during the delay:
it must cancel while preserving normal manual input. Check a no-save profile
only if one already exists; never delete a save just for testing. The mod must
not bypass first-run consent or DLC dialogs.

On any crash/unexpected load, stop, preserve the log and restore the saved DLL;
AutoContinue=0 (or remove the optional Startup section) restores ordinary menu
behavior. No install or game launch is performed by this build task. No promotion
to main/release until the user confirms behavior and explicitly authorizes it.
